## 1. 왜 상시 서버가 필요 없는가 (전략 특성 분석)

무한매수법 V4.0의 모든 주문은 **당일 장중 가격에 반응하는 주문이 아니라, 전일 종가·평단·T값으로 미리 계산되는 예약성 주문**이다:

- **매수: 전량 LOC** (일반모드 전반전/후반전, 리버스모드 쿼터매수 모두). LOC는 장 마감 전 아무 때나 접수해두면 종가 기준으로 체결 여부가 결정된다.
- **매도: 쿼터매도 LOC(별지점) + 잔량 지정가(TQQQ +15% / SOXL +20%)**. 리버스모드 첫날은 MOC 매도, 이후 LOC 매도.
- 원문도 "매일 걸어놓는다", "LOC매수 LOC매도는 예약매수로 미리 걸든, 본장에서 늦게 걸든 상관 없습니다"라고 명시.

→ **하루 2회의 배치 실행**으로 충분하다:

| 실행 | 시각(KST) | 하는 일 |
|---|---|---|
| ① 주문 배치 | 22:00~23:00 (서머타임 기준, 본장 개장 전후 여유 포함) | 전일 체결 반영된 상태로 오늘의 매수/매도 주문 계산 → 미체결 잔여 주문 전량 취소 → 신규 접수 → 접수 결과 텔레그램 보고 |
| ② 마감 정산 | 06:30~07:00 (미국 장 마감 후) | 체결내역 조회 → T값/평단/잔금 상태 갱신 → 잔고 API와 대사(reconciliation) → 일일 보고 텔레그램 발송 |

실시간 웹소켓 감시, 장중 재주문, 초 단위 타이밍이 전부 불필요하므로 **크론 실행 환경이면 무엇이든 된다** — 이것이 GitHub Actions 무료 티어로 충분한 이유다.

## 2. 증권사 선택 전략

### 2.1 요구 조건
1. 미국주식(TQQQ/SOXL) **LOC 매수/매도** — 전략의 핵심. 이것이 안 되면 자동화 자체가 불가능
2. MOC 매도 (리버스모드 첫 매도)
3. 지정가 매도 (본장~애프터 효력)
4. 미체결 주문 조회/취소, 체결내역 조회, 잔고 조회
5. 리눅스 서버(헤드리스)에서 실행 가능한 REST API — Windows OCX/COM 방식 배제

### 2.2 비교 결과

| 증권사 | 해외주식 API | 미국 LOC/MOC | 서버 실행 | 판정 |
|---|---|---|---|---|
| **한국투자증권 (KIS)** | ✅ 공식 REST (KIS Developers) | ✅ 매수 00/32(LOO)/34(LOC), 매도 00/31/32/33(MOC)/34(LOC) — 공식 샘플 코드로 확인 | ✅ REST | **채택** |
| 키움증권 | REST API는 국내주식 중심, 해외 커버리지 열세. 해외파생 API는 OCX(Windows 전용) | 미확인 | 국내 REST만 | 탈락 |
| LS(이베스트)/대신 등 | 해외주식 API 제한적 | 미확인 | — | 탈락 |
| 토스/카카오페이증권 | 공개 API 없음 | ✗ | ✗ | 탈락 |
| 해외 브로커(IBKR 등) | API 우수하나 LOC 지원, 국내 세금/환전 편의 낮음, 계좌 개설 장벽 | ✅ | ✅ | 차선 (한국 거주자에겐 KIS가 실용적) |

### 2.3 KIS API 확인된 사실 (구현 세션이 그대로 신뢰해도 되는 것)
공식 저장소 `github.com/koreainvestment/open-trading-api` 의 해외주식 샘플 코드 기준:
- 미국 매수 주문 `TTTT1002U`: ORD_DVSN `00 지정가, 32 LOO, 34 LOC` — **매수에는 MOC 없음** (전략상 매수는 전량 LOC이므로 문제 없음)
- 미국 매도 주문 `TTTT1006U`: ORD_DVSN `00, 31 MOO, 32 LOO, 33 MOC, 34 LOC`
- **모의투자(VTTT…)는 해외주식 지정가(00)만 지원** → LOC/MOC는 모의투자로 검증 불가 (§9 해결 불가능 항목 참조)
- **주간거래는 지정가만 가능** → 원문도 "주간장은 이용하지 않습니다"이므로 무관
- 접근토큰: 24시간 유효, 발급 빈도 제한 있음 → 실행 시마다 발급하되 토큰 캐시 파일 유지 권장
- 사전 절차: KIS 계좌 개설 + 해외주식 거래 약정 + KIS Developers 앱 등록(APP KEY/SECRET 발급). 계좌당 발급이므로 **지인도 각자 자기 계좌로 발급해야 함**

### 2.4 구현 세션이 반드시 재확인할 것 (문서만 믿지 말 것)
- 실계좌 소액으로 LOC 매수 1주 테스트 (모의투자로 검증 불가하므로)
- 지정가 매도 주문의 효력 세션 범위(본장만인지, 애프터까지인지) — KIS 주문 파라미터/약관 확인
- 예약주문 API(`TTTT3014U` 계열)의 접수 가능 시간대 — 22시 이전(한국 낮)에 걸고 싶다면 필요
- 휴장일 조회 API (`해외휴장일조회`) 존재 여부 및 사용

## 3. 시스템 아키텍처

```
billion-autotrader (새 private repo)
├── .github/workflows/
│   ├── place-orders.yml      # cron: 본장 개장 전후 (UTC 13:00 ≈ KST 22:00), 수동 트리거 겸용
│   └── settle-report.yml     # cron: 장 마감 후 (UTC 21:30 ≈ KST 06:30)
├── src/
│   ├── engine/               # 전략 순수 함수 (V4.0 일반/리버스, 추후 VR5.0)
│   │   ├── mubae_v4.py       #   입력: 상태+전일종가 → 출력: 주문 리스트 (부작용 없음)
│   │   └── selftest.py       #   릴리스 게이트 (웹앱 계산 결과와 교차 검증한 고정 케이스)
│   ├── broker/kis.py         # KIS REST 클라이언트 (토큰, 주문, 취소, 체결, 잔고, 휴장일)
│   ├── state.py              # 상태 로드/저장 + 잔고 대사(reconciliation)
│   ├── notify.py             # Telegram Bot 발송
│   └── main.py               # place-orders / settle-report 두 서브커맨드
├── state/                    # 계좌별 상태 JSON (Actions가 커밋으로 갱신 — git이 DB이자 감사로그)
│   └── {account}/state.json  # { mode, T, avg, shares, balance, principal, cycle, lastRun, pendingOrders }
└── config/accounts.yml       # 계좌 목록(종목/분할수/원금) — 비밀값은 넣지 않음
```

### 3.1 핵심 설계 결정
- **상태 저장 = git 커밋.** 매 실행 후 `state/*.json`을 봇이 직접 커밋/푸시. 별도 DB 불필요, 모든 상태 변화가 커밋 히스토리로 감사 가능, 롤백 = git revert. (수량계산 웹앱의 Supabase와는 **의도적으로 비연동** — "별개 프로그램" 요구사항. 추후 원하면 Supabase read-only 연동만 검토)
- **엔진은 순수 함수.** `(state, lastClose) → orders`. 웹앱의 LOCKED 파일(React 결합)은 재사용 불가하므로 재구현하되, **웹앱이 계산한 주문표와 동일한 입력→동일한 출력**을 내는 고정 테스트 케이스(최소 10케이스: 첫매수/전반전/후반전/쿼터매도 체결/소진 진입/리버스 첫날 MOC/쿼터매수/리버스 종료/큰수매수 캡/원단위 반올림)를 게이트로 두고, 게이트 실패 시 주문 실행을 차단한다 (기존 repo의 `npm run gate` 철학 동일).
- **멱등성(idempotency).** 주문 배치는 "미체결 전량 취소 → 오늘 주문표 전체 재접수" 방식. 같은 날 두 번 실행돼도 결과 동일, 중복 주문 원천 차단.
- **Fail-safe.** 실행 시작 시 (내부 상태의 보유수량/평단) vs (KIS 잔고 API)를 대사. 허용 오차 초과 불일치 → **주문 없이 즉시 중단 + 텔레그램 경보**. 사람이 확인·수정 후 수동 재트리거(workflow_dispatch).
- **비밀값은 전부 GitHub Secrets**: `KIS_APP_KEY`, `KIS_APP_SECRET`, `KIS_ACCOUNT_NO`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`. 코드/상태 파일에는 절대 미포함.

### 3.2 자동화 대상 규칙 매핑 (V4.0 → API 주문)

| 원문 규칙 | 주문 구현 |
|---|---|
| 첫 매수 (T=0): 전날 종가 +10~15% "큰수" LOC | LOC(34) 매수 1건. 큰수가는 `lastClose × 1.12` 등 설정값 (웹앱의 brokerCap=×1.18 이내) |
| 전반전 매수: 1회매수액 절반 별지점(−0.01) LOC + 절반 평단 LOC + 아래 사다리 LOC | LOC(34) 매수 N건 (웹앱 매수표와 동일한 사다리) |
| 후반전 매수: 1회매수액 전체 별지점 LOC + 아래 사다리 | LOC(34) 매수 N건 |
| 쿼터매도: 보유 1/4 별지점 LOC | LOC(34) 매도 1건 |
| 잔량 매도: 평단 TQQQ+15% / SOXL+20% 지정가 | 지정가(00) 매도 1건 |
| 리버스 첫날: 보유 1/10(20분할) or 1/20(40분할) MOC 매도 | MOC(33) 매도 1건 |
| 리버스 둘째날~: 직전보유 1/10 or 1/20 별지점 위 LOC 매도 + 잔금/4 쿼터매수 LOC 사다리 | LOC(34) 매도 1건 + LOC(34) 매수 N건. 리버스 별지점 = 직전 5거래일 종가 평균 (일일 종가 히스토리를 state에 보관) |
| 리버스 종료: 종가가 평단 대비 TQQQ −15% / SOXL −20% 위 회복 | 마감 정산 단계에서 판정 → 다음 실행부터 일반모드 |
| T값 갱신: 1회매수 +1 / 절반매수 +0.5 / 쿼터매도 ×0.75, 리버스 매도 ×0.95(40분할), 매수 +(40−T)×0.25 | 마감 정산 단계에서 체결내역 기반 갱신 |
| 증권사 ±20% 거부 대응 (큰수매수) | 모든 주문가에 `min(price, lastClose×1.18)` 캡 (웹앱과 동일 상수) |

### 3.3 텔레그램 보고 형식 (일일 1회 + 이상 시 즉시)
```

종가 38.42 (−2.1%)
체결: LOC매수 38.51×1, 41.47×1 체결 / 쿼터매도 미체결
상태: T=8.6→9.6 | 평단 38.30→38.35 | 보유 110→112주
잔금 $12,345 / 원금 $20,000 | 평가손익 +$482 (+2.4%)
내일 주문: 매수 5건(별지점 39.37…) / 매도 LOC 39.37×28 + 지정가 45.96×84
```

## 5. 보안 및 배포 (private + 무료)

- **새 repo를 private으로 생성** — private repo는 GitHub 무료 플랜에서 무제한이며, Actions도 월 2,000분 무료. "무료 + private" 요구를 정확히 충족한다. (GitHub Pages는 무료 플랜에서 public repo만 되지만, 이 봇은 웹페이지가 아니므로 Pages 자체가 불필요)
- 지인 공유: private repo에 **collaborator 초대** (무료 플랜에서 인원 제한 없음).
- API 키·계좌번호·텔레그램 토큰은 **GitHub Secrets에만** 저장. 상태 JSON에는 잔고·수량 등 민감하지만 인증정보는 아닌 데이터만 커밋.
- KIS 앱키는 **주문 권한**이 있으므로 유출 = 계좌 주문 가능. 2단계 방어: (a) Secrets는 로그에 자동 마스킹되지만 봇 코드에서 응답 원문을 로그에 찍지 않기, (b) KIS 앱 설정에서 접근 IP 제한이 가능하면 적용 검토 (GitHub Actions는 IP 가변이라 제한 시 self-hosted/VM 필요 — 트레이드오프 인지).

### 지인 다중 사용자 구조 — 법적 주의 (중요)
**타인 계좌의 매매를 내 봇이 대신 실행해주는 구조(중앙 집중형)는 무등록 투자일임업 소지가 있다.** 안전한 구조는:
- **각자 자기 계좌·자기 API 키·자기 repo(또는 fork)에서 자기 봇을 실행** — 코드만 공유. 지인은 repo를 private fork 하거나, 템플릿 repo에서 자기 것을 만들어 자기 Secrets를 넣는다.
- 하나의 repo에서 여러 계좌를 돌리는 것은 **본인 명의 복수 계좌까지만**.
구현 세션은 `config/accounts.yml` + Secrets 네이밍(`KIS_APP_KEY__{ACCOUNT}`)으로 복수 계좌를 지원하되, README에 위 주의를 명시할 것.

## 6. 라오어 원문 저작권 주의

원문에 "내용을 재가공, 편집, 정리하여 다른 공간에서 제공하는 것을 금지"라는 조항이 있다. **private repo에서 본인·지인의 개인적 사용**은 공개 제공이 아니므로 실질 문제가 낮지만:
- 이 봇/문서를 **public으로 전환하거나 블로그 등에 공개하지 말 것**
- 봇 코드 주석에 원문 전문을 옮겨 적지 말 것 (수식·파라미터 구현은 무방)

## 7. 새 저장소 분리 — 검토 결과: **분리가 명확히 유리**

| 관점 | 분리 시 |
|---|---|
| 공개/비공개 | 기존 repo는 GitHub Pages 무료 유지를 위해 public이어야 함. 자동매매는 private 필수 → 한 repo로는 양립 불가 |
| 보안 반경 | Secrets·주문 코드가 public 히스토리에 스칠 위험 원천 차단 |
| 스택 | 웹앱(Vite/React/브라우저) vs 봇(Python/헤드리스/cron) — 빌드·CI·의존성이 완전히 다름 |
| 제약 상속 | 기존 repo의 LOCKED 파일·게이트 규칙이 봇 개발을 불필요하게 구속하지 않음 |
| 커밋 소음 | 봇이 매일 state 커밋을 쌓음 — 웹앱 히스토리를 오염시키지 않음 |
| 유일한 비용 | 엔진 로직 재구현 필요 — 어차피 LOCKED React 파일은 재사용 불가하므로 실질 추가 비용 아님. 교차 검증 게이트로 정합성 보장 |

**권고: `billion-autotrader` (private) 신규 생성.** 기존 repo(이 문서 포함 부분)는 계산·시각화 담당으로 그대로 둔다.

## 9. 해결 불가능하거나 원문 그대로는 실현 불가한 것

1. **모의투자로 LOC/MOC 검증 불가.** KIS 모의투자는 해외주식 지정가만 지원. → 대체: dry-run 모드(주문 API 호출 직전까지만 실행하고 텔레그램으로 '냈을 주문' 보고) 2주 + 이후 **1주 단위 소액 실계좌** 검증. 완전한 사전 검증은 불가능함을 인지할 것.
2. **"프리장 저녁 5시부터 지정가 매도를 걸어라"의 완전 재현 불가(부분).** 원문은 지정가 매도를 프리장~본장~애프터 전 구간에 걸라고 권하나, API 주문의 효력 세션은 증권사 정책에 종속된다. 프리장 효력이 안 되면 본장 개장 시점 접수로 대체 — 평단+15~20% 지정가가 프리장에서만 체결되고 본장에서 안 될 확률은 극히 낮아 **실질 손실은 미미**하나, 원문 100% 재현은 아님.
3. **실행 신뢰성 100% 보장 불가 (무료 인프라의 본질).** GitHub Actions/무료 VM 어느 쪽도 SLA가 없다. 감지·경보·수동 복구 절차로 보완할 뿐 제거는 불가능. 돈이 걸린 시스템이므로 **일일 텔레그램 보고를 사람이 확인하는 것 자체가 마지막 안전장치**다.
4. **판단 재량의 자동화 불가.** 원문 중 "원금 재설정(복리/단리 선택)", "TQQQ→SOXL 갈아타기", 사이클 종료 후 재시작 시점 등은 투자자 재량이다. → 봇은 이런 지점에서 **멈추고 텔레그램으로 물어보는** 설계로 한다(사이클 종료 시 자동 재시작하지 않고 승인 대기).
5. **세금·환전 자동화는 범위 외.** 양도세 계산, 원화↔달러 환전 타이밍은 자동화하지 않는다(통합증거금/자동환전은 계좌 설정으로 해결).

## 10. 구현 로드맵 (다른 세션에 줄 작업 순서)

- **Phase 0 — 스캐폴딩**: 새 private repo, Python 프로젝트 구조, KIS 클라이언트(토큰/잔고/시세 조회만), Telegram 발송, Actions cron 2개(dry-run).
- **Phase 1 — 엔진**: `mubae_v4.py` 순수 함수 구현 + 교차 검증 게이트 10+케이스 (기존 웹앱 수량계산 결과를 fixture로 추출해 대조). **게이트 통과 전 주문 코드 작성 금지.**
- **Phase 2 — dry-run 운영 2주**: 실제 스케줄로 돌리되 주문 API만 미호출. 매일 '냈을 주문'을 텔레그램으로 받아 웹앱 계산과 사람이 대조.
- **Phase 3 — 소액 실전**: 원금 $500~1,000, 40분할로 실주문 개시. 체결 캡처·대사·리버스모드 전환까지 한 사이클 관찰.
- **Phase 4 — 본 운영 + 지인 온보딩**: 템플릿 repo화, README 셋업 가이드(계좌 약정→앱키→Secrets→활성화).
- **Phase 5 (선택) — VR5.0 자동화, 웹앱 Supabase 상태 read-only 연동.**

### 구현 세션에 주는 불변 원칙
1. 엔진은 순수 함수, 게이트 실패 시 주문 차단 (게이트 기대값을 코드에 맞추는 것 금지 — 기존 repo와 동일 철학)
2. 잔고 대사 실패 = 주문 전면 중단 + 경보. 어떤 경우에도 "추정"으로 주문하지 않는다
3. 인증정보는 Secrets 외 어디에도 쓰지 않는다 (로그 포함)
4. 사이클 종료·모드 전환 등 재량 지점은 자동 진행하지 않고 승인 대기
5. 이 repo(billion)의 코드는 수정하지 않는다 — 완전히 별개 프로그램이다
